The Platform-Agnostic Architecture

Every box of the governed agent-to-database architecture named by its role, with an open-source implementation and the Google Cloud guardrail side by side, the wire contract for every hop, and the same map for AWS and Azure.

The architecture in platform-agnostic terms

Agent Runtime, Agent Gateway, Model Armor and Private Service Connect are Google Cloud products. The reasons they exist are not Google-specific. Behind every one of them is a concept that any team can build from open-source parts: a reverse proxy in front of the agent, a forward proxy behind it, a content guardrail the proxies consult, a workload identity for the agent, a token exchange that narrows the user's authority, a private network link, a parameterized tool server, and a database that enforces rows and columns itself.

Figure 0A draws the architecture with those concepts only. Inside every box, a cyan line names an open-source implementation (Envoy Proxy is used for both proxies) and a green line names the Google Cloud guardrail that takes the same role in Figure 4 of Episode 01. The chapter badge points to where the box is introduced. Reading order is the same as the hop numbers: callers enter at hop 1, the agent exits at hop 4, and nothing reaches the database except hop 9.

How "Model Armor" looks without the product name

The red boxes in Figure 0A are the one component that is easiest to misread as a Google-only feature. It is not: the proxy pauses a request or response, streams the body to an external processor over gRPC, and only forwards when the processor returns a verdict. Figure 0A-2 shows the four stages that processor runs. On Google Cloud the processor is Model Armor with Cloud Sensitive Data Protection; in the open-source stack it is an Envoy ext_proc callout to a classifier such as Llama Guard with a de-identification library such as Presidio.

Figure 0A-2 — The Inline Content Guardrail is an out-of-process service the proxy consults on every request and response. On Google Cloud that service is Model Armor (with Cloud SDP for de-identification); in the open-source stack it is an Envoy ext_proc callout to a classifier.

What travels on each wire (hops 1–9)

The arrows are contracts, not just lines. Each hop has a transport, an identity that must be on the wire, and a check the receiver must perform. Hop numbers refer to Figure 0A.

HopFrom → To (Figure 0A names and numbering)Transport & wire protocolIdentity on the wireWhat the receiver must verify
Hop 1Callers & Client Apps → Ingress Reverse ProxyHTTPS (TLS 1.3) · HTTP/2 · carries traceparentEnd-user OAuth 2.1 / OIDC JWT (Token_in) from Identity Provider via Authorization Code + PKCECaller Authentication (ext_authz) validates signature against IdP JWKS, iss, aud, exp; Rate & Budget Limiter applies tenant quota.
Hop 2Event & Schedule Sources → Ingress Reverse ProxyHTTPS push · JSON event envelopeDetached HMAC-SHA256 (X-Signature, X-Timestamp, X-Nonce) or short-lived scheduler OIDC JWTRecompute HMAC over raw body; reject if older than 300 s or nonce already seen; validate schema before the agent wakes up.

Hop 4Agent Runtime → Egress Forward ProxymTLS 1.3 over TCP (or UDS with peer check) · HTTP/2Agent workload cert (SPIFFE SVID) + DPoP proof (RFC 9449) + user token Token_inCaller Proof: extract SAN URI spiffe://…, verify DPoP signature matches key bound to token (cnf.jkt).
Hop 5Egress Forward Proxy → Registry · Token Exchange · LLM · AuditgRPC / HTTPS over TLS 1.3Registry: (agent_id, user_sub, target, tool) tuple · STS: subject_token=Token_in, actor_token=SVID, audience=tools · LLM: platform model token injected by proxyDestination Authorization = Agent scope ∩ User scope against the signed registry; STS returns 5-minute, audience-bound Token_obo with act claim; model output streams back through the guardrail.
Hop 6Egress Forward Proxy → Private Network LinkTCP over L4 private tunnel · carries outer mTLS sessionSource pinned to the link's /26 range + proxy workload certOnly proxy-initiated connections cross; unsolicited connections back into the agent platform are dropped.
Hop 7Private Network Link → Private Endpoint & DNSPrivate L4 routing (RFC 1918) + split-horizon DNSNetwork provenance (VPC + attachment id) + caller identityData Perimeter ingress rule requires both an allowed identity and an allowed source network.
Hop 8Private Endpoint → Parameterized Tool ServerMCP Streamable HTTP (HTTP/2 POST + JSON-RPC 2.0) over mTLSTransport: proxy client cert · Header: downscoped Token_obo (or KMS-signed context JWT for jobs)Tool server checks aud, extracts verified_sub = Token_obo.sub, validates arguments against JSON Schema; the model never supplies the user id.
Hop 9Parameterized Tool Server → DatabaseWarehouse: HTTPS/gRPC per query · OLTP: TLS 1.3 on the DB wire protocol via a poolWarehouse: per-query bearer Token_obo · OLTP: short-lived IAM DB token for the tool-server identity + $1 = verified_sub (or SET LOCAL)Database executes prepared statements only; Row-Level and Column-Level Security filter for verified_sub; writes go through SECURITY DEFINER procedures.
