The Platform-Agnostic Zero-Trust Agent-to-Database Architecture

Every component, wire protocol, Envoy filter (`ext_authz` / `ext_proc`), cryptographic token, and cross-cloud mapping explained from first principles.

1. Platform-Agnostic Zero-Trust Blueprint (Before Vendor Mapping)

Products like Vertex AI Agent Engine, Google Cloud Agent Gateway, and Model Armor are cloud-specific implementations of deeper architectural primitives. In any production environment—whether you run on Google Cloud, AWS, Azure, or self-hosted Kubernetes—the security of an agent-to-database connection depends on 16 vendor-agnostic building blocks across 5 trust zones and 10 cryptographically verified wire hops.

In the platform-agnostic reference diagram below (Figure 0A), Envoy Proxy serves as the policy enforcement point at both Ingress (B1) and Egress (B3), and content safety ("Model Armor") is represented by its underlying architectural pattern: an inline Envoy External Processor (ext_proc) gRPC Guardrail + Deterministic DLP Tokenizer.

Figure 0A — The Platform-Agnostic Zero-Trust Reference Architecture. Every component is defined by its architectural role, wire protocol, and cryptographic contract rather than a cloud vendor product name.

2. Representing "Model Armor" Vendor-Agnostically: Inline Envoy ext_proc gRPC Pipeline

In a vendor-agnostic architecture, prompt and tool-output screening is not a magic cloud checkbox—it is an out-of-process gRPC External Processor (envoy.filters.http.ext_proc) wired into both the Ingress Envoy Proxy (B1, screening user prompts and final replies) and the Egress Envoy Proxy (B3, screening outbound MCP tool arguments and inbound database rows before they enter the LLM context window).

Figure 0A-2 — Vendor-Agnostic Representation of "Model Armor": an Envoy External Processor (`ext_proc`) gRPC service that canonicalizes, classifies, and tokenizes payloads inline with `failure_mode_allow: false`.

3. Wire-by-Wire Connection & Communication Protocol Contract (Hops 1–10)

Every arrow in Figure 0A represents a strict network and cryptographic contract between two boxes. If a connection lacks any of the transport, framing, or identity properties listed below, an attacker can bypass the control plane.

Hop Source → Destination Transport & Wire Protocol Identity & Credential on the Wire What the Receiver Must Verify
Hop 1 A1 Client App → B1 Envoy Ingress HTTPS (TLS 1.3) · HTTP/2 or gRPC-Web · Carries traceparent header End-user OAuth 2.1 Bearer / OIDC ID Token (T1) obtained via Authorization Code + PKCE from A2 Verify TLS 1.3; call ext_authz to validate JWT signature against A2 JWKS, check iss, aud, exp, and apply per-tenant token bucket rate limits.
Hop 1b B1 Envoy Ingress → A2 Identity Provider HTTPS (TLS 1.3) · GET /.well-known/jwks.json (cached with short TTL) Public OIDC Discovery / mTLS client authentication for introspection Verify IdP TLS certificate chain and pin expected issuer URI (iss).
Hop 2 A3 Event & Cron Bus → B1 Envoy Ingress HTTPS Push (TLS 1.3) · HTTP/2 POST JSON event envelope Detached HMAC-SHA256 Signature (X-Signature-256 + X-Timestamp + X-Nonce) or short-lived Scheduler OIDC JWT Recompute HMAC over raw body; reject if |now - timestamp| > 300s or if nonce exists in Redis replay cache; validate JSON schema.
Hop 3 B1 Envoy Ingress → B2 Agent Runtime Pod Localhost Loopback / UDS (sidecar) OR mTLS over HTTP/2 (gateway) Ingress Envoy SPIFFE X.509 SVID + Envoy-signed internal header containing verified user_sub & tenant_id Agent Runtime rejects any connection not coming from B1 Envoy's SPIFFE identity; strips untrusted external headers; receives canonicalized, DLP-tokenized prompt.
Hop 4 B2 Agent Runtime → B3 Envoy Egress mTLS 1.3 over TCP (or Unix Domain Socket with peer credential check) · HTTP/2 Agent SPIFFE X.509 SVID (spiffe://corp/ns/ai/sa/agent-01) + RFC 9449 DPoP Proof JWT + User Token T1 B3 Envoy terminates mTLS, extracts SAN URI (spiffe://...), and verifies the DPoP header signature matches the public key bound (`cnf.jkt`) to the token.
Hop 5a B1 / B3 Envoy ↔ ext_proc Guardrail Bi-directional gRPC Stream over mTLS (envoy.service.ext_proc.v3.ExternalProcessor) Mutual SPIFFE X.509 SVIDs between Envoy and Guardrail service Envoy sets failure_mode_allow: false; waits for explicit ProcessingResponse (`CONTINUE` with tokenized body or `ImmediateResponse 403`).
Hop 5b B3 Envoy Egress → C2 Capability Registry gRPC over mTLS (envoy.service.auth.v3.Authorization.Check) Tuple: (agent_spiffe_id, user_sub, target_mcp_uri, tool_name, http_method) Evaluates Dual-Scope Intersection (Agent Allowed Tools ∩ User RBAC Scopes) against signed Registry manifest; returns `OK` or `PERMISSION_DENIED`.
Hop 5c B3 Envoy Egress → C3 OAuth 2.1 STS / KMS HTTPS (TLS 1.3) POST /oauth2/token (RFC 8693 Token Exchange) subject_token = T1 (User JWT), actor_token = Agent SPIFFE JWT-SVID, audience = mcp://db-read, scope = orders:read STS verifies both tokens and issues a short-lived (5-min), audience-restricted OBO Token T2 containing sub: user_123 and act: {sub: spiffe://.../agent-01}.
Hop 5d B3 Envoy Egress → C1 LLM Inference API HTTPS (TLS 1.3) / gRPC · Streaming or Unary inference call Platform-injected short-lived model-invoker token (attached by B3 Envoy, never held by B2) Model receives only DLP-tokenized prompt + approved tool declarations; model output is streamed back through B3 ext_proc before reaching B2.
Hop 6 B3 Envoy Egress → D1 L4 Private Bridge TCP over L4 Private Tunnel Interface (`10.10.9.2/28`) · Carries outer mTLS 1.3 session Source IP pinned to dedicated Private Bridge CIDR (`10.10.9.0/28`); carries B3 Envoy SPIFFE X.509 cert Unidirectional initiation: B3 → D1 allowed; unsolicited connections from Data VPC back into Agent DMZ are dropped at L4.
Hop 7 D1 L4 Private Bridge → D2 Private Endpoint & DNS Private L4 Routing (RFC 1918) + Split-Horizon DNS resolution (mcp.internal → 10.10.2.20) Network provenance metadata (VPC ID + Bridge Attachment ID) + Caller Identity Zone 4 Data Perimeter verifies that both the caller identity (`agent/toolbox`) and source network (`D1`) satisfy the Perimeter Ingress Policy.
Hop 8 D2 Private Endpoint → D3 Parameterized MCP Server MCP Streamable HTTP (HTTP/2 POST + JSON-RPC 2.0) over mTLS 1.3 1) Transport: B3 Envoy client X.509 cert
2) Header: Downscoped OBO Token T2 (or KMS-signed Context JWT for async jobs)		 D3 verifies client mTLS cert belongs to B3 Envoy, validates T2 signature and aud == mcp://db-read, extracts verified_sub = T2.sub, and validates tool args against JSON Schema.
Hop 9 D3 Parameterized MCP Server → D4 Database Engine Mode A (Analytical HTTP): HTTPS / gRPC Storage API
Mode B (OLTP Pooled TCP): TLS 1.3 + mTLS over DB Wire Protocol (e.g., pgwire :5432)		 Mode A: Per-query OAuth 2.1 Bearer Token T2
Mode B: Short-lived IAM DB Auth token for toolbox-sa + server-bound parameter $1 = verified_sub (or SET LOCAL app.current_user_id)		 Database executes pre-compiled prepared statement (never model-written SQL), evaluates Row-Level Security (RLS) and Column-Level Security (CLS) for verified_sub, and enforces SECURITY DEFINER stored procedures for writes.
Hop 10 B1, B2, B3, D3, D4 → C4 OpenTelemetry & Audit Sink OTLP / gRPC over TLS 1.3 + Control-Plane Immutable Log Stream Service workload identity with write-only (`appendOnly`) permission to WORM log bucket Correlates every hop under a single W3C traceparent (`trace_id`) and records both actor_id (spiffe) and subject_id (user_sub).
