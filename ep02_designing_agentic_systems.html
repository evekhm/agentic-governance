A Mental Model for Designing Agentic Systems

A 20-minute design exercise for a self-healing code repository, and the twelve questions that turn three wishes into a design.

By Eva Khmelinskaya · November 2026 · about 15 minutes to read

It is tempting to treat an AI agent as a genie in a bottle. You state the wish, and the result appears: an agent that finds the problem, an agent that fixes it, an agent that ships the fix. We put language models into systems precisely for that flexibility—so we no longer have to anticipate and hardcode every trajectory in advance. As frontier models improve and earn trust in everyday work, handing them a vague goal and watching them figure out the steps becomes routine. The more capable they get, the easier it is to draw each agent as an autonomous black box that just works.

At the same time, the tooling around these models moves fast. New frameworks, SDKs, and APIs keep arriving, and there is always another interface to learn. Underneath that churn, the architectural questions change far more slowly. This post is the checklist I wrote to shift my own mental model and keep myself from treating every agent like a black box that will figure it out on its own—one drawing and twelve questions that I can reuse on any system of this kind.

The Task

This episode is set up as a design exercise that aims for about twenty minutes—intentionally tight, so you have to focus on the right priorities instead of getting lost in details.

The task: Design a self-healing code repository system with three agents: an agent that detects issues, an agent that suggests a fix, and an agent that opens a pull request with the fix. It is expected to handle 10,000 deployments a day across 20 to 30 repositories, of which 1% fail.
Challenge yourself before reading on. Take a few minutes and think about how you would design this system. What would you draw first? Which questions come to mind, and which would you ask before calling the design finished?

The Genie in the Bottle

This is the point where I used to go wrong. Each agent in Figure 1 has a clear job, and the three jobs together cover the task. So the drawing looks finished, and the next step seems to be picking a model and writing three prompts.

Naming what each agent does is not an architecture. Each box is still a sealed bottle, and it is easy to let the model inside stand in for every unanswered question:

  • How does the first agent tell a bug in the code from an outage in a shared service? It figures it out.
  • What if the fix from the second agent is wrong? It will test it.
  • What does the third agent need from the second? Whatever the second one found.

To carry one failure through the whole post, here is the running example.

The running example: At 14:00 the payments repository deploys commit a3f91c2. A canary instance starts failing with KeyError: 'vat_rate' in payments/tax.py. The new code reads a tax rate that is missing for one country. The right fix is a few lines in tax.py and a test for the missing case.
The Skeleton

The Skeleton Most Agent Systems Share

The agents are the small part. Most of the system is the plain machinery around them.

For every box in an architecture diagram, first ask what goes wrong without it. If you cannot name the failure mode it prevents, you do not need the box.

The rule that organizes the whole design “The model does the reading and the trying. Code does the deciding, the counting, and the writing.”

The Playbook

Twelve Questions for Any Agentic System

Ask them in this order. Each card shows what breaks if you skip it, what to decide, and how it applies to the self-healing repo.

Before drawing
1

What wakes the system up, and what is in the wake-up message?

Skip it and…
  • You design for one trigger and miss two others.
  • Every agent has to understand every sender's format.
  • Someone puts 50 MB of logs inside a queue message.
Decide
  • List every source that can start the work.
  • Normalize into one common message: id, source, subject, exact version, duplicate key, and a pointer to the data.
In the self-healing repo
  • Sources: CI, the CD controller, and post-deploy monitoring.
  • FailureEvent(repo, commit_sha, failure_fingerprint, log_pointer).
2

How big is it really?

Skip it and…
  • You spend time sizing model capacity for the headline number.
  • You optimize for throughput when the real problem is correctness.
Decide
  • Multiply headline volume by failure rate to get events per day and per hour.
  • Name what kind of problem that makes it: scale, or correctness and safety.
  • Estimate cost per case, cache static instructions, and escalate to stronger models or higher thinking only on retries.
In the self-healing repo
  • 10,000 × 1% = 100 failures a day, about 4 an hour.
  • Attempt 1 uses a fast model (LOW thinking) with cached repo rules; only RETRY escalates.
3

What must happen in seconds, and who does it?

Skip it and…
  • Users wait minutes while a model diagnoses the bug.
  • The agent ends up holding control of live production traffic.
Decide
  • Find the fast, model-free control that already exists: rollback, block, rate-limit, fallback.
  • Keep containment in existing tooling. The agents work on a second clock afterwards.
In the self-healing repo
  • The CD controller halts the canary and rolls back in seconds.
  • The agents repair the code afterwards and never touch live traffic.
The plumbing
4

How does work get from the event to a worker without being lost?

Skip it and…
  • The sender times out waiting for a slow model run.
  • A burst drops events.
  • Anyone can post fake events to the endpoint.
Decide
  • Put a small receiver in front: verify the sender, filter noise, reply at once.
  • Put a queue between receiver and worker; acknowledge only at completion.
  • Retry with exponential backoff (model quota errors included) and dead-letter after N failures.
In the self-healing repo
  • Webhook receiver → Pub/Sub → worker job.
  • Verify signature, reply 200 in under a second, dead-letter after 5 tries.
5

How do I avoid doing the same thing twice?

Skip it and…
  • Fifteen identical pull requests, tickets, or refunds.
  • A retry repeats a write that already succeeded.
Decide
  • Compute a deterministic key in code from stable fields—never by a model.
  • Keep one durable record per key with an explicit state.
  • Check the record before working, and pass an idempotency key on the write.
In the self-healing repo
  • failure_fingerprint: hash of error type, code location, and cleaned message.
  • One incidents row per (repo, failure_fingerprint): IN_PROGRESS, PR_OPENED, ESCALATED.
6

How do I tell one problem from everything being on fire?

Skip it and…
  • A shared registry or base-image outage makes every worker "fix" healthy code.
  • Token budget burns and humans get flooded.
Decide
  • Maintain a shared, short-window count of distinct things failing.
  • Above a threshold, trip a circuit breaker, park incoming work, and alert once.
  • Provide a manual kill switch, and let one probe through after cool-off.
In the self-healing repo
  • Redis set of distinct repos failing in the last 5 minutes.
  • 5 or more repos → pause PR creation for 15 minutes and page on-call.
7

What happens when a worker dies halfway?

Skip it and…
  • Acknowledged on receipt: the work is lost when the worker crashes.
  • Locked with no expiry: the work stays stuck forever.
Decide
  • Acknowledge the queue message only after the final step succeeds.
  • Claim work with a lease that expires, and renew it on a heartbeat while alive.
  • Right before any external write, re-check ownership (fencing) and that the target has not moved on.
In the self-healing repo
  • Pub/Sub redelivery if the worker dies.
  • 120-second lease in the incident row, renewed every 30 seconds; fencing check before opening the PR.
The agents and the harness
8

Which steps need a model, which are code, and what is the harness?

Skip it and…
  • "Three models chatting": unpredictable, unbounded, impossible to audit.
  • A model grades its own work (and agrees with its own mistakes).
  • An agent runs on a host with credentials and cannot isolate itself.
Decide
  • Give each step the least autonomy that works (four-row test). If each of ten model steps is right 95% of the time, all ten are right about 60% of the time.
  • Wrap the model steps in a harness: the code around the model that owns state, what each model sees, retry counters, secrets, and sandboxes.
  • Fix the control flow as a graph when every case follows the same steps or a mistake is costly. Let the model choose its steps only for open-ended, supervised work.
In the self-healing repo
  • Agent 1 (Detect): rules + one schema-bound call, no tools.
  • Agent 2 (Fix): bounded loop. Its tools run in Sandbox 1 (no network, no IAM).
  • Verifier and Agent 3 (Open PR): plain code. The verifier also rejects a patch that deletes or skips tests.

        return Event(route="ESCALATE", output={"reason": "protected_path"})
    result = run_sandbox_tests(patch.unified_diff)  # --network=none, 0 creds

    attempts = ctx.state.get("fix_attempts", 0) + 1
    ctx.state["fix_attempts"] = attempts
    if attempts < 3:

    return Event(route="ESCALATE", output={"reason": "max_attempts_exhausted"})

What Is Deployed

The three agents are not three deployments. They are nodes of one workflow graph inside one worker service. The guard is the first node: plain code that decides whether this case should run at all. Agent 1 and Agent 2 are model nodes. Agent 3 is a function node, and so are the guard, the verifier, and the escalation step. One queue message starts one run of the graph, and the message is acknowledged when the run ends.

Agent 2's model calls leave from the worker, which can reach the model endpoint. Only its tools run in the sandbox, which has no network and no credentials.

A node becomes its own service only for a reason: it needs a different identity or network boundary, it scales differently, or another team owns it. The typed contract between the two stays the same.

9

What passes between the agents, and who decides what is next?

Skip it and…
  • Each agent reinterprets the previous one's prose; errors compound.
  • Injected text travels straight into the agent that can act.
  • A retry loop has no exit.
Decide
  • Use typed contracts with a few validated fields—never raw chat history.
  • Keep routing (PASS, RETRY, ESCALATE) and retry counters in code.
  • If subtasks run in parallel, keep helper subagents read-only and leave writes to one owner.
In the self-healing repo
  • FailureEvent → IncidentReport → ProposedPatch.
  • The verifier returns one of three routes; capped at 3 attempts.
  • Agent 1 may answer flaky or unknown: no patch, escalate.
10

Where does the data live, and how does the agent read it?

Skip it and…
  • A pre-built copy goes stale or drops access rules.
  • The model gets flooded with whole files or noisy stack traces.
  • Models poison shared long-term memory across runs.
Decide
  • Leave data where it lives; read by pointer with strict bounds (version, time window, line range).
  • Read with the identity whose permissions should apply, and give each component the least it needs.
  • Keep tools narrow with bounded output. Operational state is written by code, not by models.
In the self-healing repo
  • Repo checked out at exact failing commit_sha (no stale search index).
  • Pointer tools (ripgrep_search, read_file_lines) and truncated test output; 100 error lines max.
Safety and launch
11

What would an attacker do with it?

Skip it and…
  • Text an outsider controls reaches a model that can run tools.
  • Model-written code runs next to real cloud credentials.
  • Write permissions are wider than the job requires.
Decide
  • Mark where untrusted input enters; give that reader no tools.
  • Run generated code in a sandbox with no network and no credentials.
  • Keep write permission narrow and enforced in code. Irreversible actions wait for a person.
In the self-healing repo
  • Webhook signature, content screening, and toolless Agent 1.
  • Sandboxed tests, protected-path check, GitHub App limited to autofix/*, draft PRs.
12

How do I switch it on, and how do I know it is working?

Skip it and…
  • A noisy bot is muted by engineers within a week.
  • You have no evidence that it is safe to grant more autonomy.
Decide
  • Offline evals: run a golden replay set before launch and on every prompt, model, or tool change (track pass@1 vs. pass@3).
  • Online evals & rollout: launch in stages (shadow → drafts → bounded) and track live human acceptance with automatic demotion.
  • Keep one trace per case: every model call, tool call, and verdict.
In the self-healing repo
  • Offline replay gates every change against historical fixes.
  • Online: shadow → draft PRs → ready-for-review; watch PRs merged without edits and human diff-edit distance.

Summary

One-Page Cheat Sheet

The rule, the order, and the twelve questions in a few words each.

The rule The model does the reading and the trying. Code does the deciding, the counting, and the writing.

The order is the path of one event through Figure 2A: it arrives (1 to 3), survives the plumbing (4 to 7), passes through the agents (8 to 10), and is allowed to act (11 and 12). For every box, name what breaks without it.

Before drawing
  • 1 · Wake-up. Every trigger. One normalized message with a pointer to the data.
  • 2 · Size. Volume × rate. Scale problem or correctness problem? Cost per case.
  • 3 · Seconds. An existing, model-free control contains. The agents work afterwards.
The plumbing
  • 4 · Intake. Receiver, queue, acknowledge at the end, backoff, dead-letter.
  • 5 · Twice. Key computed in code, one record per key, idempotent write.
  • 6 · Storm. Count distinct failures, circuit breaker, kill switch.
  • 7 · Crash. Expiring lease, heartbeat, re-check before the write.
The agents and the harness
  • 8 · Model or code. Least autonomy that works. The harness owns state, context, retries, secrets, sandboxes.
  • 9 · Handoffs. Typed contracts. Code routes: pass, retry, escalate.
  • 10 · Data. Read in place, by pointer, bounded. Least-privilege identity. Code writes the state.
Safety and launch
  • 11 · Attacker. The reader of untrusted text has no tools. Sandbox. Narrow writes. A person on irreversible actions.
  • 12 · Launch. Replay set, then shadow, draft, bounded. One acceptance number, automatic demotion, a trace per case.

In a design session of about twenty minutes: questions 1 to 3 first, then draw Figure 2A and walk one event through it (Q4, Q8, Q9), go deep on two of Q5, Q6, Q7, or Q11, and finish with Q12.
