A Mental Model for Designing Agentic Systems

Starting from three black-box wishes and growing them—question by question—into a reliable hybrid architecture.

By Eva Khmelinskaya · November 2026 · about 15 minutes to read

It is tempting to treat an AI agent as a genie in a bottle: you state a wish, and the result appears. As frontier models improve and earn trust in everyday work, handing them a vague goal and watching them figure out the steps becomes routine. The more capable they get, the easier it is to carry that habit into system design and draw each agent as an autonomous black box that just works.

At the same time, the tooling around these models moves fast. New frameworks, SDKs, and APIs keep arriving, and there is always another interface to learn. Underneath that churn, the architectural questions change far more slowly. Like Episode 01, this episode starts with the simplest possible diagram and grows it across six stages—adding only the boxes and boundaries that twelve design questions force onto the page.

Design Scenario

This episode is framed around a twenty-minute design exercise—intentionally tight, so you focus on structural invariants rather than getting lost in framework details.

Scenario: Design a self-healing code repository system with three agents: an agent that detects issues, an agent that suggests a fix, and an agent that opens a pull request with the fix. It is expected to handle 10,000 deployments a day across 20 to 30 repositories, of which 1% fail.

Why Use a Language Model at All—and Why Wrap It in Code

Before adding a single box to Figure 1, ask why plain deterministic software cannot solve the problem on its own. Classical code excels whenever inputs arrive in fixed schemas and every transformation from input to action can be written ahead of time as explicit rules. It breaks down at two boundaries that recur across domains: interpreting unstructured, noisy inputs whose phrasing and format vary too widely for static parsers or regular expressions, and exploring an open-ended solution space where the next lookup or candidate change depends on what the previous step uncovered. Language models earn their place in an architecture at those two points, because non-deterministic reasoning generalizes across unfamiliar inputs and synthesizes candidate actions that could never be enumerated in advance as rules.

At the same time, the exact property that gives a model that reach—probabilistic generation over open-ended context—makes it the wrong mechanism for system invariants such as deduplication, storm limits, lease ownership, self-grading, or holding write credentials. Production systems combine both in a hybrid architecture that embeds scoped agents inside deterministic workflows (Anthropic; Google Cloud; Cognition; 12-Factor Agents). That split rests on a general asymmetry: proposing a structured interpretation or candidate fix from messy context is hard to write as rules, whereas verifying whether a candidate output satisfies schema, policy, and test suites—and committing the side effect once—is exact in deterministic code. Skip it and…

Live traffic is now safe while the workflow takes minutes—yet upstream callers still post directly to the worker and lose events on bursts or crashes. Stage 2 fixes intake.

Stage 2 of 6 · Question 4 · Reliable Intake & Terminal Ack

Decouple Callers from Slow Runs with a Receiver and Queue

Authenticate fast at the edge, buffer work durably, and acknowledge only when a run finishes.

Where we are

Webhooks from CI or monitoring time out after a few seconds, whereas testing a candidate fix takes minutes. Inserting a stateless receiver, a durable queue, and a terminal acknowledgement (ack) path in Figure 3 prevents dropped events.

Figure 3 — Stage 2 of 6 (Q4): Stateless receiver, durable queue, and terminal ack decouple callers from slow runs.

4

How does work get from the event to a worker without being lost?

Skip it and…
  • The webhook sender times out waiting for a slow model run.
  • A burst drops events, or an unverified endpoint accepts spoofed webhooks.
Decide
  • Place a stateless Receiver in front: verify sender signature/token, drop healthy noise, reply 200 at once.
  • Buffer in a durable Queue; send ack only at a terminal exit, with exponential backoff and a dead-letter queue after N crashes.
In the self-healing repo
  • Webhook receiver → Pub/Sub → worker.
  • HMAC/OIDC check, reply in <100 ms, ack at PR_OPENED / SKIP / ESCALATED, DLQ after 5 crashes.
Added in Stage 2: Stateless Ingress / Receiver + durable Queue + terminal ackStill open: Duplicate deliveries · multi-repo outage storms · dead or stalled workers · black-box agents

At-least-once queueing guarantees no event is lost, which immediately creates the opposite hazard: the same failure delivered twice, a shared outage flooding every repo, or a worker dying mid-run. Stage 3 adds coordination.

Stage 3 of 6 · Questions 5–7 · Coordination, Storms & Crash Recovery

Guard Against Duplicates, Outage Storms, and Mid-Run Crashes

One transactional coordination store gives the worker a lock, an expiring lease, a fencing check, and a storm breaker.

Where we are

Because queues deliver at least once and CI retries webhooks, two workers can pull the same bug at the same time—or a broken base image can break twenty repositories at once. Figure 4 adds a deterministic Dispatcher / Guard backed by a transactional Coordination store & kill switch. Three related safeguards on the case row prevent race conditions: an atomic lock (only one worker claims the case), an expiring lease renewed by heartbeats (so a crashed worker's claim expires after 120 seconds instead of staying stuck forever), and a monotonic fencing generation number checked right before writing (so if Worker A stalls past 120 seconds and Worker B takes over at generation 2, Worker A is blocked from writing late).

Figure 4 — Stage 3 of 6 (Q5–Q7): Dispatcher guard, storm breaker, kill switch, and expiring case lease added.

5

How do I avoid doing the same thing twice?

Skip it and…
  • Fifteen identical pull requests, tickets, or refunds open for one bug.
  • A retry repeats an external write that already succeeded.
Decide
  • Compute a deterministic duplicate key in plain code from stable fields—never by a model.
  • Keep one durable row per key (`IN_PROGRESS`, `DONE`, `ESCALATED`) and pass an idempotency key on external writes.
In the self-healing repo
  • failure_fingerprint: hash of error type, code location, and cleaned message.
  • One row per (repo, failure_fingerprint); finished rows immediately ack and skip.
6

How do I tell one problem from everything being on fire?

Skip it and…
  • A shared registry or compiler outage makes workers "fix" twenty healthy repositories.
  • Token budget burns and engineers get flooded with bad PRs.
Decide
  • Count distinct targets failing over a short sliding window.
  • Above a threshold, trip a circuit breaker, pause automated writes, and page a human once; provide a manual kill switch.
In the self-healing repo
  • 5-minute query of distinct failing repos in the coordination database.
  • 5 or more repos failing → pause PR creation for 15 minutes and page on-call.
7

What happens when a worker dies halfway?

Skip it and…
  • ack on receipt: in-flight work vanishes when a worker crashes.
  • Permanent lock without expiry: the case stays stuck in IN_PROGRESS forever.
Decide
  • ack only after a terminal state is recorded.
  • Claim the row with an expiring lease renewed on a heartbeat, and verify the lease generation (fencing) right before any external write.
In the self-healing repo
  • 120-second lease renewed every 30 seconds; unacknowledged crashes redeliver via Pub/Sub.
  • Lease generation checked right before opening the draft PR.
Added in Stage 3: Dispatcher / Guard + Coordination store (lock, expiring lease, fencing, storm breaker, kill switch)Still open: The three agents are still unexamined purple black boxes

The plumbing around the worker is now reliable. Stage 4 opens up the three purple boxes themselves and asks which ones should be models at all.

Stage 4 of 6 · Question 8 · Autonomy Split, Dual-LLM & Harness

Open the Black Boxes: Dual-LLM Separation, Verifier, and Plain-Code Gate

Give every step the lowest autonomy that works, separate untrusted reading from tool use, and wire control flow in code.

Where we are

Up to Figure 4, all three scenario agents were drawn as identical purple boxes. Question 8 breaks that illusion in Figure 5. Inside the deterministic worker (the harness—the plain-code controller around the models), the two genuine model steps follow the Dual-LLM pattern (Willison; formalized with capability enforcement in CaMeL, and examined for ADK session-history isolation in Episode 01): Agent 1 becomes a toolless Quarantined LLM that turns untrusted log text into a fixed schema, while Agent 2 becomes the Privileged LLM permitted to invoke workspace tools in a bounded loop. Between Agent 2 and Agent 3 we insert a deterministic Verifier so the model never grades its own work, and Agent 3 turns green as a plain-code Act gate—because opening a pull request follows a fixed rule and needs no language model at all.

Figure 5 — Stage 4 of 6 (Q8): Black boxes split into Quarantined LLM, Privileged LLM, plain-code Verifier, and Act gate.

8

Which steps need a model, which are code, and what is the harness?

Skip it and…
  • "Three models chatting": unpredictable routing, unbounded loops, impossible to audit.
  • A model grades its own patch and agrees with its own mistakes.
  • A model holds repository write tokens just to call a deterministic REST endpoint.
Decide
  • Apply the four-row autonomy test (Table 1). If each of ten model steps is right 95% of the time, all ten succeed together ~60% of the time.
  • Split untrusted reading (Quarantined LLM, zero tools) from tool calling (Privileged LLM, bounded loop).
  • Wrap both in a deterministic harness that owns routing, retry counters, verification, and credentials.
In the self-healing repo
  • Agent 1 (Quarantined LLM): 1 schema-bound call over ≤100 screened lines, no tools.
  • Agent 2 (Privileged LLM): bounded tool loop with step and time caps.
  • Verifier & Agent 3 (Act gate): plain deterministic code, zero LLM calls.

How the ADK Workflow Sketch Works

To enforce the structure in Figure 5 rather than letting agents hand off to one another in free-form prose, the sketch below wires the worker as an explicit ADK 2.x Workflow graph (self_healing_workflow). ADK's edges list mixes plain Python functions and LlmAgent nodes in one deterministic state machine: "START" runs dedup_and_circuit_breaker (the Guard), whose returned route selects detector_agent ("ANALYZE"), skip_node ("SKIP"), or escalate_node ("ESCALATE"). When analysis runs, detector_agent (Quarantined LLM) passes a validated IncidentReport to route_incident, a plain function that diverts "flaky" or "unknown" reports straight to escalate_node and routes actionable bugs ("FIX") to fixer_coding_agent (Privileged LLM), which hands a typed ProposedPatch to verify_patch_in_sandbox.

Inside verify_patch_in_sandbox(ctx, patch), plain code owns both policy enforcement and loop termination. First, touches_protected_path blocks edits to sensitive paths and immediately returns Event(route="ESCALATE"). Next, run_sandbox_tests tests the diff in a fresh container with --network=none and zero credentials. On a pass, Event(route="PASS") forwards the verified patch to open_draft_pr (Agent 3). On a failure, code increments ctx.state["fix_attempts"]: while fewer than three attempts have run, Event(route="RETRY") sends at most 2000 characters of stderr back to fixer_coding_agent; on the third failure, Event(route="ESCALATE") guarantees termination.

The same graph sketched with ADK 2.x Workflow (agent and helper definitions omitted)
from google.adk import Agent, Context, Event, Workflow

def verify_patch_in_sandbox(ctx: Context, patch: ProposedPatch) -> Event:
    if touches_protected_path(patch.target_files):
        return Event(route="ESCALATE", output={"reason": "protected_path"})
    result = run_sandbox_tests(patch.unified_diff)  # --network=none, 0 creds
    if result["passed"]:
        return Event(
            route="PASS",
            output={"patch": patch, "stdout": result["stdout"]},
        )
    attempts = ctx.state.get("fix_attempts", 0) + 1
    ctx.state["fix_attempts"] = attempts
    if attempts < 3:
        return Event(route="RETRY", output={"stderr": result["stderr"][:2000]})
    return Event(route="ESCALATE", output={"reason": "max_attempts_exhausted"})

self_healing_workflow = Workflow(
    name="self_healing_code_repo",
    edges=[
        ("START", dedup_and_circuit_breaker),
        (dedup_and_circuit_breaker, {
            "ANALYZE": detector_agent,
            "SKIP": skip_node,
            "ESCALATE": escalate_node,
        }),
        (detector_agent, route_incident),              # typed IncidentReport handoff
        (route_incident, {"FIX": fixer_coding_agent, "ESCALATE": escalate_node}),
        (fixer_coding_agent, verify_patch_in_sandbox), # typed ProposedPatch handoff
        (verify_patch_in_sandbox, {
            "PASS": open_draft_pr,                    # Agent 3: plain code + PR token
            "RETRY": fixer_coding_agent,              # code-owned back-edge
            "ESCALATE": escalate_node,
        }),
    ],
)

Stage 5 of 6 · Questions 9–10 · Typed Handoffs, Retries & State

Define Typed Handover Artifacts, Bounded Retries, and Memory Ownership

Pass small validated schemas instead of chat history, cap retries, escalate cleanly, and keep models from writing long-term memory.

Where we are

Separating the Quarantined LLM from the Privileged LLM fails if the runtime silently forwards shared conversation history—including raw untrusted logs—into Step 2 (Episode 01), or if a failed patch loops forever. Figure 6 lights up the four typed handover artifacts (→ FailureEvent, → IncidentReport, → ProposedPatch, → Draft PR), adds the bounded RETRY (< N) back-edge and ESCALATE to person exit, and introduces per-run Session, pointer-addressed blobs, and read-only long-term memory of human-approved cases.

Figure 6 — Stage 5 of 6 (Q9–Q10): Typed handoff artifacts, bounded retry (< N), human escalation, and session/memory stores.

9

What passes between the agents, and who decides what is next?

Skip it and…
  • Each step reinterprets the previous model's prose; errors compound.
  • Shared session history leaks raw untrusted text past the Quarantined LLM into the Privileged LLM.
  • A retry loop has no exit.
Decide
  • Pass small typed contracts validated in code—never raw chat history (set include_contents="none").
  • Keep routing (PASS, RETRY, ESCALATE) and retry counters in deterministic code.
  • Give the classifier an explicit abstain exit (flaky / unknown → escalate).
In the self-healing repo
  • FailureEvent → IncidentReport → ProposedPatch → Draft PR.
  • Verifier caps retries at N = 3; flaky or unknown skips patching and escalates.
10

Where does the data live, and how does the agent read it?

Skip it and…
  • A pre-built search index lags behind the failing commit or drops permissions.
  • Whole files and 50 MB stack traces flood the model's context window.
  • Unverified model guesses get saved into shared long-term memory and poison future runs.
Decide
  • Read data in place by pointer with strict bounds (exact version, time window, line range).
  • Keep per-run step state in a session store and large payloads in object storage.
  • Make cross-run long-term memory read-only during a run; update it in code only after human approval.
In the self-healing repo
  • Check out the exact failing commit_sha; bound tools (ripgrep_search, read_file_lines) and cap logs at 100 lines.
  • Long-term memory holds only past human-merged fixes, written post-merge by code.

Who Owns Which State

A single store cannot serve every state need in an agentic workflow: cross-worker locks and storm limits require atomic database transactions, per-run step history and raw blobs belong to one execution, and long-term memory across runs must never be written by an unverified model loop. One danger remains: Agent 2 and the Verifier execute repository code and candidate patches, and the system still needs a safe way to ship and measure quality. Stage 6 completes the generic architecture.

Stage 6 of 6 · Questions 11–12 · Security Isolation, Rollout & Completed Skeleton

Isolate Code Execution, Gate Writes, and Measure Rollout

Put untrusted execution in credential-free sandboxes, keep a human on irreversible writes, and gate every change with offline and online evals.

Where we are

Running repository tests or model-written diffs inside the worker container would expose cloud identity and repository tokens to arbitrary code execution, and launching without replay metrics leaves engineers guessing whether the bot helps or creates noise. Adding isolated sandboxes (Sandbox 1 and Sandbox 2), a human review loop, and the Audit and eval store in Figure 7 completes the reusable generic architecture.

11

What would an attacker do with it?

Skip it and…
  • Injected log text steers a tool-calling model.
  • Malicious test code or a crafted diff steals cloud IAM or GitHub tokens from the worker host.
  • Over-broad write scopes allow pushes to main or edits to CI workflows.
Decide
  • Keep the Quarantined LLM toolless (Dual-LLM / CaMeL) and sever shared history.
  • Execute the Privileged LLM's tools and the Verifier's test suite inside ephemeral sandboxes with zero network and zero credentials.
  • Enforce protected-path rules and narrow write scopes in code; keep a human on irreversible actions.
In the self-healing repo
  • HMAC check, content screening, and toolless Agent 1.
  • Sandbox 1 (Agent 2 tools) and fresh Sandbox 2 (Verifier pytest) with --network=none and 0 credentials.
  • Protected-path blocklist, token restricted to autofix/* branches, draft PRs only.
12

How do I switch it on, and how do I know it is working?

Skip it and…
  • A noisy bot opens broken PRs and gets muted by engineers within a week.
  • Prompt or model upgrades silently regress accuracy with no safety net.
Decide
  • Offline evals: gate every prompt, tool, or model change against a golden replay set (tracking pass@1 and pass@3).
  • Online rollout: progress through stages (shadow → draft → ready-for-review) with automatic demotion on human rejection spikes.
  • Record one end-to-end trace per case across every call and verdict.
In the self-healing repo
  • Replay historical repository bugs before every release.
  • Shadow mode → draft PRs → ready-for-review; track merge-without-edit rate and human diff-edit distance.

What Gets Deployed as Its Own Service

Drawing several steps in a workflow graph often tempts teams to deploy every box—especially every agent—as a separate microservice over HTTP. Turning sequential steps of the same task into separate network services adds extra hops, serialization bugs, authentication policies, and partial-failure modes for zero gain. By default, workflow nodes—both LlmAgent steps and plain functions—run in-process inside a single worker service, where one queue message drives one complete run of the graph.

Split a step out into its own standalone deployment or runtime boundary only when one of four conditions holds:

  • Different ingress or latency contract: a public endpoint that must answer callers in milliseconds cannot block on a multi-minute agent run.
  • Security and isolation boundary: untrusted code or test suites must not execute inside the container that holds cloud identity or external write tokens.
  • Independent scaling or hardware: one step needs GPUs, large memory, or scales at a completely different rate than the rest of the graph.
  • Separate team ownership: a capability is owned and released independently by another team behind an explicit API or tool contract.

Applying those four criteria produces the exact two-service layout in Figure 8: a lightweight Cloud Run Receiver at the public webhook edge, and one Worker Service (on Cloud Run or Agent Runtime) running all workflow nodes in-process—dispatching only untrusted tool and test execution across an isolation boundary into ephemeral, credential-free Code Execution sandboxes while keeping model calls and the pull-request token on the worker.
